# 架构评审与优化报告

> 评审对象：`F:\08.个人计划网站\00.健康管理网站架构方案.md`（v0.1）
> 评审依据：真实资产交叉核对（见第二节证据清单）
> 评审日期：2026-09-04
> 结论：v0.1 主体方向正确，予以保留；但数据字典、知识库源、约束口径三处与真实资产脱节，需修订为 v0.2。

## 一、执行摘要

v0.1 的核心设计经得起推敲，**以下 6 项原样保留**（详见第五节）：聊天驱动 + 记录确认卡的交互范式、"AI 永不直接写库"的信用控制、三重闸（Schema→Pydantic→确认卡）、`raw_text` 溯源、SQLite + FTS5 起步、Provider 抽象 + SSE 流式。

但把 v0.1 与磁盘上的真实文件逐字段核对后，发现三类**必须修正**的偏差：

1. **数据字典与真实记录表脱节**——v0.1 §2.3 假设饮食是单列，真实是 5 个独立列；且虚构了数据里根本不存在的字段，同时漏掉了方案的核心抓手（奶茶/夜饿/力量/腰围）。
2. **知识库源路径错误 + 未识别两代方案并存**——v0.1 指向的 `D:\桌面\健康管理\` 不存在；真实 KB 在 `F:\01.健康管理\`，且它与 8 月的 `plan.docx` 是**两代不同方案**（三阶段 vs 两阶段、100kg vs 108.55kg 基线），v0.1 把两代概念混用却未锁定权威源。
3. **约束与示例失真**——全文用 72.3kg、20–200kg 举例，真实基线约 107kg；入睡跨零点语义、docx 表格迁移均未覆盖。

修订动作已全部并入 `00.健康管理网站架构方案.md` v0.2，本报告与文档 §0 变更日志互为索引。

## 三、关键发现：两代方案并存（v0.1 混用）

这是本次评审最重要的结构性发现。磁盘上存在**两代不同方案**，v0.1 未加区分地混用了两代的概念：

| 维度 | 7 月版（`F:\01.健康管理\`） | 8 月版（`Hugo\s-plan\`） |
|---|---|---|
| 制定日期 | 2026-07-24（7-25 修订） | 2026-08-30 |
| 定位 | 广义健康管理（减脂增肌 + 激素 + 中医 + 习惯） | 聚焦减脂作战（血糖稳定化） |
| 阶段结构 | **三阶段**（适应/进阶/巩固，共 24 周） | **两阶段**（冲刺 8.31-9.20 / 稳态 9.21+） |
| 基线体重 | 100kg（BMI 32.7） | 108.55kg（BMI 35.4） |
| 追踪维度 | 补剂/饮水/血检/体征/疼痛评分/肠胃/腰围/照片 | 晨夜重/三餐/加餐/奶茶/游泳/力量/步数/入睡/夜饿 |
| 补剂细节 | 有（VitD3 + 锌精确剂量） | 无 |

**混用证据**：v0.1 §2.3 的 `food.stage(菜单阶段)` 标注"三阶段菜单"（来自 7 月版），而 §8.2 的"9.21 开学转稳态期"来自 8 月版；§2.3 `supplement` 的 VitD3+锌来自 7 月版，而要迁移的 xlsx 是 8 月版。两者基线相差 8.55kg（7 月 100kg → 8 月 108.55kg，期间反弹），阶段数也不同。

**风险**：若不锁定权威源，AI 会拿 7 月的三阶段/100kg 基线去解释 8 月的记录，或把 8 月的两阶段目标套到补剂问题上，导致建议自相矛盾。

**裁定（已与用户确认）**：
- **8 月减脂作战方案 = 当前主线**：减脂执行、阶段划分、体重/腰围目标、血糖稳定化、奶茶夜宵零食三座大山，一律以 `plan.docx` 为准。
- **7 月健康管理计划 = KB 背景**：补剂剂量、激素/抗雌化、中医调理、就医红线以 `F:\01.健康管理\` 为准（因 8 月 docx 无补剂细节）。
- 广义健康维度（血检/体征/饮水/疼痛评分/中医/习惯/照片）**列为 P3 可选**，不入 v0.2 主线数据模型。
- 落地机制：`kb_chunks` 增 `source_plan` 与 `section_no` 字段；系统提示显式声明主线与背景的分域，禁止混用两代基线与阶段。

## 四、分级问题清单

严重度：P0 = 阻断落地/数据错误；P1 = 影响核心体验正确性；P2 = 影响完备性；P3 = 增强项。

### P0-1 数据字典与真实 xlsx 列脱节（§2.3）
- **问题**：v0.1 记 `food | meal, stage, adherence, desc | xlsx 饮食列`，假设单一"饮食列"。
- **证据**：真实为 5 个独立列 `E 早餐 / F 午餐 / G 晚餐 / H 加餐 / I 奶茶甜饮`，均为自由文本，**无 stage、无 adherence 字段**。
- **改法**：拆为 `meal`（slot=breakfast/lunch/dinner/snack）与独立的 `sweet_drink`（level 枚举）两类；删除虚构的 stage/adherence。
- **影响章节**：§2.3、§5、§8.1。

### P0-2 核心行为维度缺失（§2.3）
- **问题**：v0.1 的 8 类记录漏掉方案的多个核心抓手。
- **证据**：`I 奶茶/甜饮`（方案明列为"三座大山"之一、有 3.4 戒断路线图、下拉档位）、`N 夜饿处理`（下拉 没饿/加餐预案/破戒，对应"血糖稳定化→夜宵不需要"主线）、`K 力量训练`（v0.1 exercise 只提 swim）、`腰围 cm`（每周日 KPI，v0.1 误并入 body 症状的 level）。
- **改法**：新增 `sweet_drink`、`night_hunger` 两类；`exercise` 扩为 kind∈{swim,strength}；`waist` 独立为数值 KPI 类型。
- **影响章节**：§2.3、§5、§7.2、§7.3、§10(P2)。

### P0-3 知识库源路径错误（§6.4/§8.1）
- **问题**：v0.1 写源为 `D:\桌面\健康管理\（8 个编号 md）`。
- **证据**：该路径**不存在**；真实 8 个编号 md 在 `F:\01.健康管理\`（00~07 + 健康管理计划.md + 补充.md）；8 月方案为 `D:\桌面\Hugo\s-plan\plan.docx`；xlsx 内引用的 `减脂方案_2026-08-30.md` 在磁盘上无同名 md（对应内容即 plan.docx）。
- **改法**：全文路径改为真实路径；`import_kb` 同时处理"md 直读"（7 月）与"docx→md"（8 月）两类源。
- **影响章节**：§6.4、§8.1、§9、§12。

### P0-4 两代方案权威源未锁定（§6.4）
- **问题**：见第三节。v0.1 未意识到两代并存。
- **改法**：`kb_chunks` 增 `source_plan∈{august_fatloss, july_health}` + `section_no`；系统提示锁定分域权威；禁止混用基线与阶段。
- **影响章节**：§5、§6.1、§6.4、§6.5、§6.6、§11。

### P1-1 体重约束与示例失真（§1/§2.1/§2.3）
- **问题**：全文用 72.3kg 举例、约束写"20–200kg"。
- **证据**：真实基线约 107kg（起始 108.55）。20–200kg 过宽，抓不住"10.7 误输/单位错"这类真实错误。
- **改法**：示例改为真实量级（如"今早空腹 106.8，昨晚 00:30 睡"）；约束改为**绝对 40–200kg + 相对上次确认值 ±5kg 双闸**（超限确认卡标红复核，非硬拒，避免真实暴增暴减被误杀）。
- **影响章节**：§1、§2.1、§2.3、§6.3、§11。

### P1-2 入睡跨零点语义缺失 + 虚构 quality（§2.3）
- **问题**：v0.1 `sleep | bedtime, quality`，范围"0–24h"，未定义跨零点归属。
- **证据**：真实 M 列有 `00:30`、`00:00`（凌晨入睡）；使用说明口径为"填几点躺下"；**无 quality 列**。
- **改法**：删除 quality；定义规则——`bedtime` 存为该夜所属日的时刻，`bedtime<12:00` 视为跨零点（次日凌晨）但仍归属记录日；AI 解析"昨晚 X 点睡"且 X<12 时 date 归到前一日。
- **影响章节**：§2.3、§6.3、§8.1。

### P1-3 SSE 事件契约未定义（§6.1）
- **问题**：v0.1 说"多字段拆多卡排队确认"，但未定义流式事件协议。
- **改法**：明确 `event: token / record_card / done` 三类事件，支持一句话（晨重+入睡）触发多张 card 排队；补入 P1 实现清单。
- **影响章节**：§6.1、§7.2、§10(P1)。

### P1-4 枚举抽取与校验缺失（§6.3）
- **问题**：v0.1 三重闸只针对数值，未覆盖枚举字段。
- **证据**：奶茶档位、夜饿、力量 done、补剂 timing 都是枚举；自由文本→枚举存在模糊（"一大杯可乐"应映射为"全糖"而非按甜度猜测）。
- **改法**：闸二增加"枚举合法性校验"（值必须∈枚举）；模糊项由确认卡下拉兜底纠正；确认卡从"数值+槽位"扩展为支持枚举字段。
- **影响章节**：§6.3、§7.2。

### P2-1 迁移未处理真实数据形态（§8）
- **问题**：v0.1 "按行读入"未考虑空行、公式、多 sheet。
- **证据**：xlsx 有预填未来空行、`体重趋势` sheet 含 `#DIV/0!` 公式、`使用说明` sheet 是口径文档。
- **改法**：只导真实数据行（跳过空行）；不导公式错误值，改把 初始晨重 108.55/腰围 110/阶段目标 写入 settings 作基线参数；`使用说明` 作 KB 口径补充；给出逐列映射表。

### P2-2 docx 表格迁移风险（§8.1）

- **改法**：`import_kb`/`docx2md` 遍历段落 + 表格转 md，保留章节号锚点（3.4/5.2/6.1...）以供溯源引用。

### P2-3 异常识别规则窄于方案（§6.7/P2）

## 五、保留项说明（v0.1 正确、无需改）

以下设计经评审确认合理，v0.2 原样保留，避免过度改造：

1. **聊天为主入口 + 记录确认卡**：符合"记录零门槛"目标，交互范式正确。
2. **AI 永不直接写库**：信用控制的正确根基，杜绝自动入账风险。
3. **三重闸（Schema→Pydantic→确认卡 + raw_text）**：对抗数值幻觉的分层设计正确（v0.2 仅在闸二补枚举与相对合理性校验）。
4. **SQLite + WAL + FTS5 起步**：单用户 MB 级数据、零运维、单文件易备份；KB 规模小，FTS5（bm25）足够，不必上向量库——判断正确。
5. **Provider 抽象（OpenAI 兼容 + 能力位）**：DeepSeek/通义/GLM/Kimi/Ollama 均兼容，切换成本低；不支持 tools 时降级"约束 JSON + 正则兜底"的思路正确。
6. **SSE 而非 WebSocket**：对话打字机场景下更简单可靠——选型正确（v0.2 仅补齐事件契约）。
7. **依赖最小化**（无重型 UI 框架、无微服务、薄 httpx Adapter）：契合个人长期维护，正确。
